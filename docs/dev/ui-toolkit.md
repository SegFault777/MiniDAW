# UI toolkits

MiniDAW has two Qt-free UI toolkits, both without external libraries:

- **`src/ui`** - the small software-rendering toolkit of the Native version. On Windows only the finished pixel buffer is copied to the window.
- **`src/vulkan`** - the GPU toolkit of the Vulkan version. It builds a vertex list every frame; a backend draws it.

# Part 1: `src/ui` (Native)

## Components
| File | Role |
| --- | --- |
| `Canvas.*` | ARGB pixel buffer, clipping, anti-aliased shapes (rounded rectangle, circle, arc, triangle, line), text, **translation lookup** |
| `FontData.*` | Built-in font table (Liberation Sans 11/13 px regular and bold), generated by `tools/gen_font.py`. ASCII only |
| `Ui.h`, `Ui.cpp` | `NativeUi`: control bar, toolbar, arrangement, mixer, status bar, drawing the menus |
| `UiInput.cpp` | Mouse, keyboard, the menu definitions, file operations |
| `UiDialogs.cpp` | Parameter dialogs (transform, quantize, bounce, preferences, ...) |
| `UiEditors.cpp` | The bottom panels: inspector, devices (knobs), piano roll, steps, Drummer, automation |
| `UiBrowser.cpp` | The browser panel and drag and drop |
| `Dialog.*` | The modal dialog widget |

## Key idea 1: immediate-mode hit testing
Whenever `paint()` draws a control it **registers the click area and the action together** (`addHit`, `uiSlider`, `uiAction`, `uiKnob`). Mouse events look for the top-most entry of the list that the last `paint()` produced. The drawing and the click area therefore cannot drift apart, and adding a control takes code in one place.

```cpp
uiAction(c, {x, y, 76, 22}, "Mute", [this, ti, ri] { m_s.setRegionMute(ti, ri, true); });
uiSlider(c, rect, "Volume", t01, "-3.0 dB", [this, ti](double t) { m_s.setVolume(ti, faderToGain(t)); }, color);
uiKnob(c, cx, cy, 20, "Cutoff", t01, "5000 Hz", setFn, resetFn, color);
```
Editors with their own geometry (piano roll, step grid, automation lane) only register the area (`Hit::PianoGrid` and so on) and compute the mouse themselves.

## Key idea 2: two widths
`m_winW` is the whole window and `m_w` is the **width of the arrangement and the bottom panel** (window width minus browser width). The control bar, toolbar, status bar, menus and dialogs use `m_winW`; the rest use `m_w`. When the browser is toggled, `relayout()` recomputes `m_w`.

## Key idea 3: translation where it is drawn
`Canvas::text`, `textWidth` and `fit` look the string up **by its English original** in the translation table (`Canvas::setTranslations`) before drawing. UI code therefore writes plain English and never `tr()`. To translate, add "original<TAB>translation" to `translations/*.tsv`.
For messages that contain numbers or names use the **`%1` placeholder pattern**, as in `NativeUi::msg("Saved %1", path)`, and put the pattern itself into the table.

## Text renderer
By default the built-in font (ASCII). On Windows `Win32App.cpp` installs a GDI renderer (`GdiText`) that draws Unicode including Korean. Implementing only `ui::TextRenderer` lets you switch to another renderer (DirectWrite and so on).

## Dialogs
`Dialog` only collects values; the caller applies them to the `Session` in the OK callback.
```cpp
openDialog(std::make_unique<Dialog>("Transpose",
    Dialog::Values{Field::number("Interval", last("transpose", 12), -48, 48, 1, 0, " semitones")},
    [this, t, r](const Dialog::Values& v) { m_s.transposeRegion(t, r, int(v[0].value)); }));
```
Field kinds: `number`, `slider`, `check`, `choice`, `input` (text), `note` (explanation), `button`. The last used values are remembered in `m_last`. Keyboard input arrives through `WM_CHAR` -> `NativeUi::text()`, other keys through `key()`.

## Coordinates and constants
At the bottom of `Ui.h`: `kControlH=54`, `kToolbarH=32`, `kRulerH=26`, `kHeaderW=236` (width of the track header and x origin of the timeline), `kStatusH=22`, `kMixerH=344` (the whole bottom panel), `kBrowserW=250`. The track height is `m_trackH` (34/60/96).

## Adding a new screen element
1. Add the needed `Hit` kind and state variables to `Ui.h`, and put `drawXxx` into the `paint()` flow.
2. Draw controls with `uiAction` / `uiSlider` / `uiKnob`. If the mouse reaction is special, add a `case Hit::Xxx` to the `switch` in `mouseDown`.
3. If a status-bar hint is needed, add a line to `hintFor()`.
4. Add a test that feeds input, plus a screenshot, to `tests/ui_tests.cpp`.
5. Put new English text into the four `.tsv` files (`tests/platform_tests.cpp` checks some keys).

# Part 2: `src/vulkan` (Vulkan)

## Components
| File | Role |
| --- | --- |
| `Draw.*` | `DrawList`: one vertex type (36 bytes), SDF rounded rectangles, lines, glyphs, clip batches. Applies the DPI scale and pixel-snaps corners |
| `Text.*` | `Fonts`: a 1024x1024 glyph atlas and `FontSource` (built-in font, or GDI on Windows). A full atlas is handled by `consumeOverflow`; a per-frame time budget for new glyphs is `setFrameBudgetMs` (see *Glyph budget*) |
| `SoftRaster.*` | A CPU renderer using the same formulas as `shaders/ui.frag`: used for tests and screenshots |
| `Gui.*` | The immediate-mode toolkit: `interact`, `button`, `slider`, `knob`, `fader`, `textField`, `numberField`, `dropdown`, `menu`, `tooltip`; double-click detection (0.4 s, 5 px); IME composition (`setPreedit`, `imeCaret`) |
| `Theme.h`, `Icons.h` | Colours and sizes; icons drawn from shapes |
| `Studio.h` | The DAW screen class and all its state |
| `Studio.cpp` | Frame loop, layout, menu bar, transport, status bar, palette (`Ctrl+K`), help (`F1`), shortcut routing |
| `StudioArrange.cpp` | Ruler, track headers, lanes, regions, tools, drags, context menus, zoom, Tab to Transient, Ripple Delete, workspaces |
| `StudioDock.cpp` | Mixer, devices, snapshots, inspector, browser |
| `StudioEditors.cpp` | Piano roll (Logic / Ableton style), step sequencer, automation, the audio editor (`drawAudioEditor`, `trimAtPlayhead`) |
| `StudioDialogs.cpp` | The parameter-dialog engine, every `dlg*`, file operations, preferences |
| `StudioCommands.cpp` | The command registry |
| `VkRenderer.*` | The Vulkan backend (`vulkan-1.dll` is loaded at run time, so only the headers are needed to build) |
| `VkMain.cpp` | The Win32 shell (window, input, GDI glyphs, IME messages, the device-list cache, audio / MIDI / plug-ins / settings) |
| `shaders/ui.vert`, `ui.frag` | GLSL 450, compiled to `.spv` at build time and placed in `shaders/` next to the exe |

## Vertex format
`loc0` position, `loc1` uv, `loc2` shape (`hx`, `hy`, `r`, `s`), `loc3` colour. A rounded rectangle is one quad whose fragment computes a signed distance; lines and glyphs use the same vertex type. Keep `SoftRaster.cpp` and `ui.frag` in step: a change to one is a change to the other.

## Immediate mode
Each frame `Studio` rebuilds the whole `DrawList` (about 10,000 vertices for a normal project). `g.interact(rect, id)` returns hover / press / drag state in the same place where the control is drawn, so drawing and input cannot disagree.

## The command registry
Every function is a row in `StudioCommands.cpp` (`addCmd`): label, shortcut, an optional "enabled" condition and the action. The menus, the `Ctrl+K` palette, the `F1` sheet and the shortcut router all read the table. A label starting with `~` is a hidden alias that only the palette finds. Commands with an enabled condition may share a key (for example `Z` = typing octave / zoom to fit).

## Glyph budget
Rasterizing a glyph through GDI can take milliseconds (Windows font linking for Korean and Japanese), and a dialog or a tutorial page needs hundreds of new ones in one frame. `Fonts::setFrameBudgetMs(ms)` (8 in `VkMain.cpp`; 0 = off, the default, so the tests and the other UIs never skip anything) limits the time spent on new glyphs per frame. `VkMain` calls `beginFrame()` before each draw pass; a glyph over the budget is returned empty and **not cached**, `takePending()` becomes true and `renderFrame` marks the window dirty, so the next frame continues at once and the message loop is served in between. Placeholder glyphs have an estimated advance, so text may re-wrap for a frame or two; do not cache text widths anywhere (nothing does today).

## IME
`Gui::setPreedit(utf8)` is the text that the IME is composing. The focused `textField` draws it at the caret in the accent colour with an underline and moves the caret behind it; the real string only changes when the platform commits (`onText`). `Gui::imeCaret(x, y, h)` gives the caret in window coordinates (valid after a frame with a focused field) so `VkMain` can place the composition and candidate windows. In `VkMain.cpp`: `WM_IME_STARTCOMPOSITION` is swallowed (no system window), `WM_IME_COMPOSITION` delivers `GCS_RESULTSTR` through `onText` and `GCS_COMPSTR` through `setPreedit` (and does not call `DefWindowProc`, so no `WM_CHAR` duplicates). `syncIme` takes the input context away (`ImmAssociateContext(hwnd, nullptr)`) while `Gui::textFocused()` is false, so a keyboard in Hangul mode still sends real key events for shortcuts, and gives it back with `ImmAssociateContextEx(..., IACE_DEFAULT)`. A committed character and `Enter` can arrive in the same frame: `textField` inserts the pending text before it handles `Enter`.

## Device lists
`Host::audioDevices` / `Host::midiDevices` are called when Preferences opens, and enumeration can block for seconds. `VkMain` keeps a `DeviceCache` filled by a worker thread (`Host::refreshDevices`, started at the start and each time Preferences opens); the callbacks only read the cache, and `Host::devicesReady` is false until the first reading is done, in which case `Studio::dlgPreferences` shows a message instead of the dialog. A `Host` without these two optional callbacks (the tests) behaves as before.

## The audio editor
`Studio::drawAudioEditor` (Editor tab, audio region selected). State: `m_aeZoom` (1-64), `m_aeScroll` (the part of the region at the left edge), `m_aeFade` (the fade a handle drag is changing), `m_aeWave` (the waveform rectangle, `audioEditorWave()` for tests). Handles move the fade by the mouse delta, not to the mouse position, so grabbing does not jump and zoom needs no special case. A grab is its own undo step (`checkpoint()` once, then `setRegionAudio(..., undoStep = false)`). The playhead click, trim buttons and zoom use the same visible window (`s0`, `vis`).

## Translation
`Studio::tr` looks the English original up in `core::TranslationTable`. New English text works at once; adding the four translations to `translations/*.tsv` is separate work.

## Adding a screen element
1. Draw and handle input in one place with `g.interact` in the right `Studio*.cpp`.
2. If it is a function, add it as a command first and let the menu / shortcut come from the table.
3. In `tests/vulkan_tests.cpp` add the input simulation and a screenshot.
